# Commit87 high-level roadmap

**Based on:** [10 November 2026 assessment](assessment-2026-11-10.md),
snapshot `28525c26e93f083d244afec854c1e6b1ddf4fefb` (`0.2.0-beta.5`).

For file-level starting points, work packages and acceptance checks, see the
[implementation plan](../implementation-plan-2026-11-10.md).

## Direction

Preserve Commit87's system-Git foundation, Electron process split and focused repository
workflows. Establish a finite work-preservation and correctness milestone before expanding
remote authoring. The sequence below describes outcomes, not a ticket-by-ticket plan or
calendar commitment.

## 1. Protect work and authority — immediate priority

- Make file and ref actions affect exactly their intended targets; preserve submodule recovery
  data and prevent stale conflict content from reaching another file.
- Bind credentials to authorized destinations and align privileged IPC/console capabilities
  with the documented renderer trust model.
- Verify ownership of the actual update replacement target.
- Ensure PR checkout selects the contributor's head and release creation honors or rejects
  requested visibility semantics.
- Correct misleading recovery/security claims and add regression evidence for these defects.

**Exit signal:** the identified unintended-loss and credential/update-destination cases are
closed with meaningful temporary-repository/boundary checks and relevant real-app validation.
This is a bounded correction milestone, not a claim of exhaustive security assurance.

## 2. Make daily workflows dependable — next

- Preserve repository identity and truthful success/conflict/failure outcomes across operations.
- Make staged/unstaged review, renames, drafts, graph filters and tab/task lifetimes coherent.
- Complete keyboard review and dialog interactions; keep empty, failed and unsupported states clear.
- Make advertised bare-clone completion/opening and provider operations match their actual capabilities.
- Provide a short setup, authentication and recovery path for users and contributors.

**Exit signal:** representative prepare–review–commit and conflict/recovery workflows remain
correct through navigation, interrupted operations and expected failures.

## 3. Make release confidence explicit — alongside release preparation

- Unblock fresh development startup and keep version/channel classification consistent through
  build, verification and publication.
- Define production signing/update policy and verify artifacts before publishing them.
- Validate native installation/update boundaries for supported targets; repair optional recipes
  or clearly designate them experimental.
- Narrow release credentials and strengthen dependency/action provenance proportionately.
- Reuse existing native CI jobs for relevant behavioral checks, backed by a small real-Electron
  critical-flow gate and strict provider fixtures.

**Exit signal:** a release carries current evidence for its claimed support tier, and channel,
publisher and installation/update expectations match what users actually receive.

## 4. Improve measured scale and choose the next feature — then

- Reduce repeated repository discovery and bound task output using the existing architecture.
- Measure large-file, large-history and many-worktree cases before choosing caching or virtualization.
- Extract repeated policy from change hotspots as those improvements are made.
- Reassess Git LFS visibility versus inline PR review using user workflows and demand. Keep the
  next feature slice narrow enough to validate end to end across its supported providers.

**Exit signal:** performance work has measured benefit, and feature expansion addresses a
demonstrated need without weakening the established correctness boundaries.

## Decisions to preserve

Keep system Git, one constrained IPC transport, the existing state library, main-owned
networking/secrets, explicit update installation and grouped architecture publication where
channel metadata is shared. Prefer focused policy/request fixes over a rewrite, arbitrary
file-size refactoring, universal coverage percentages or an always-live test-account dependency.

The final feature order, recoverable-discard contract, prerelease first-run channel and supported
platform/provider tiers remain product decisions. Review them at the readiness milestone rather
than treating this assessment as a fixed long-term specification.
